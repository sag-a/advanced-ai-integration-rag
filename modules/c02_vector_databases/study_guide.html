01 / Destination

Five things to be able to explain.

  1. Why we store the original text and metadata alongside each embedding.
  2. How a question becomes a vector and retrieves the nearest stored chunks.
  3. What exact search and approximate search promise—and what they do not.
  4. How a category filter changes the eligible results.
  5. Why changing a document can require recomputing its embedding.
Your opening sentence

“In Chapter 1, we searched vectors held in Python memory. Now we store those vectors in a database so we can reuse them, search them, and manage the underlying documents.”

This chapter retrieves passages. It does not generate an answer, call Claude, or require an Anthropic key. A future rag_pipelines chapter will take retrieved passages as evidence for generated answers.

First study the concepts through section 4. Then follow M01 and M02. Keep query-plan tuning as instructor background; participants do not need to understand every Python helper.

02 / Two separate flows

Prepare documents once. Search many times.

Ingestion: when documents are added or changed

1 · LoadRead the support document.
2 · SplitCreate manageable text chunks.
3 · EmbedNomic converts each chunk into 768 numbers.
4 · StoreSave ID, text, metadata, and vector.

Retrieval: whenever somebody asks a question

1 · Ask“I was charged twice.”
2 · EmbedNomic creates the question vector.
3 · SearchThe database finds nearby document vectors.
4 · ReturnRead the retrieved passages and their scores.

In both demos, Nomic runs locally in Python. M01 explicitly computes vectors before sending them to PostgreSQL. In M02, the Chroma client automatically calls the configured embedding function when given documents or question text; its Docker server stores and searches the vectors.

What carries over from Chapter 1?

The fictional telecom_support.txt, recursive character splitting, the same encoder, and cosine-based retrieval.

What is new?

Persistent records, database search, an index, metadata filters, and controlled changes to stored records.

The current fixture yields six chunks. Both demos set chunk size to 500 characters and overlap to 50 characters. Recursive boundaries mean the actual overlap can be smaller; 50 is a setting, not a guarantee at every boundary.

03 / Data model

One chunk, four pieces of information.

Illustrative Chroma record from the billing topic
FieldExampleWhy keep it?
IDtelecom-003Retrieve, update, or delete the same record reliably.
Document text“Check whether two entries are completed payments…”Return readable evidence to the application.
Metadatacategory: billing, source, language, chunk number, modelFilter results and trace a passage back to its source.
Embedding768 floating-point numbersCompare the passage with a question numerically.

The embedding is useful for matching. It does not replace the source text or provide a dependable way to reconstruct it.

The embedding agreement

  • Model: nomic-ai/nomic-embed-text-v2-moe; this course uses 768 dimensions.
  • Document input: search_document: followed by the chunk.
  • Question input: search_query: followed by the question.
  • Shared loader: attention-mask mean pooling, then L2 normalization.
  • Maximum input: 512 tokens including the prefix. Characters used for chunking and model tokens are different units.
Same length does not mean same embedding space.

Two different models can both return 768 numbers without those numbers being comparable. Changing the encoder or its preprocessing generally requires re-embedding documents. The course uses separate v2 database names to keep the old vectors apart.

Code reference: shared local embedding loader. The standalone demos check model metadata and dimensions. M02 also validates the saved embedding-function contract. These checks are not a complete production migration system.

04 / Ranking

Closer vectors become retrieval candidates.

Cosine similarity compares vector direction. For these normalized embeddings, the dot product gives the same similarity. Cosine distance is 1 − cosine similarity.

Invented numbers for explanation—not measured model results
PassageCosine similarity ↑Cosine distance ↓Rank
Duplicate charge0.820.181
Understanding your bill0.670.332
Wi-Fi troubleshooting0.210.793

Top-k means “return up to k nearest candidates.” It does not mean “return k correct answers.” If the question is unrelated to every document, a nearest-neighbor search can still return something.

A similarity of 0.82 is not an 82% probability of correctness. Cosine similarity can range from −1 to 1; it is not restricted to positive values.

Ask the class: “If we ask this telecom collection for a cake recipe, does requesting the top three results make them relevant?”

Expected answer: no. Relevance checks, answer grounding, and abstention belong to the broader RAG workflow. A universal similarity threshold should not be assumed; calibrate decisions using representative questions and labels.

05 / m01_pgvector_demo.py

Vectors inside PostgreSQL.

pgvector adds vector storage and distance operators to PostgreSQL. Your demo stores content and JSONB metadata beside a vector(768) column. Official pgvector introduction ↗

StageWhat students seeUnderlying file
setupEnable the extension; create the schema and table.01_setup.sql
insertEmbed six chunks; save or update matching IDs.02_insert.sql
indexBuild the HNSW cosine index and update planner statistics.03_index.sql
searchEmbed a question; run nearest-neighbor SQL.04_search.sql
explainCompare query plans and returned IDs.Python module

The SQL to explain on screen

SELECT id, content, metadata,
       embedding <=> %(query)s AS cosine_distance,
       1 - (embedding <=> %(query)s) AS cosine_similarity
FROM rag_pgvector_demo_nomic_v2.documents
ORDER BY embedding <=> %(query)s
LIMIT %(top_k)s;

Read it aloud: “Compare each eligible stored vector with the question, order by smallest distance, and return the first k passages.” The %(query)s and %(top_k)s placeholders are bound by Python’s database driver; this is not a standalone psql command.

The direct distance expression in ORDER BY supports the matching vector index. Rewriting it as ORDER BY cosine_similarity DESC does not give the index-compatible form. pgvector query-plan guidance ↗

Repeated inserts: ON CONFLICT updates existing IDs, avoiding duplicate rows. It does not remove obsolete extra rows if you later shrink the dataset.

06 / Instructor background

Exact search, approximate search, and evidence.

Exact search in this demo

Compare against all stored vectors, then sort. It establishes the nearest-neighbor baseline under the chosen metric.

Think: inspect every book’s matching score before picking the closest.

HNSW search

Navigate a multilayer graph of connected vectors to find promising neighbors without comparing every vector.

Think: follow broad shortcuts, then explore locally. A closer vector can be missed.

HNSW stands for Hierarchical Navigable Small World. Its graph contains vector records; it is not a knowledge graph of entities and facts. The index adds storage, build, and maintenance costs. Search effort can be increased to improve recall at the expense of latency. HNSW and its parameters ↗

What the three query plans demonstrate

  1. Exact: disable index and bitmap scans for this transaction.
  2. Normal: let PostgreSQL choose. With six rows, a sequential scan can be sensible.
  3. Encouraged HNSW: discourage sequential scans for this transaction; verify an HNSW index scan appears.

The demo compares returned IDs and exact/HNSW top-k overlap, and checks that planner settings are restored afterward. It does not establish a general speedup or quality result.

Two different meanings of recall

ANN recall: did approximate search recover the neighbors found by exact search? Retrieval relevance recall: did the system retrieve the passages humans marked as useful? Perfect ANN recall can still retrieve irrelevant material if the embedding representation ranks it poorly.

EXPLAIN shows the plan. EXPLAIN ANALYZE actually executes the query and reports observations. Separately, ANALYZE table updates planner statistics. Read the first sections of PostgreSQL’s EXPLAIN guide; detailed planner costs are optional.

For a meaningful performance experiment, keep data, queries, hardware, filters, and k constant; compare latency and neighbor recall on a larger corpus. Do not infer a production benefit from six rows.

07 / m02_chroma_demo.py

The same retrieval idea through a collection API.

A Chroma collection holds records with IDs, documents, embeddings, and metadata. The demo uses collection rag_chroma_demo_nomic_v2_auto, cosine distance, and embedding_function=NomicEmbeddingFunction(). Chroma automatically embeds the text through that configured function. The previous explicit-vector collection is preserved.

OperationPurposeIn your demo
create_collectionPrepare the store.Configure cosine distance and validate collection metadata.
addAdd new IDs with their data.Existing fixture IDs are skipped, not refreshed.

Configure once, then work with text

collection = client.create_collection(
    name="my_nomic_collection",
    embedding_function=NomicEmbeddingFunction(),
    configuration={"hnsw": {"space": "cosine"}},
)
collection.add(ids=["doc-1"], documents=["Check duplicate payments with billing."])
collection.query(query_texts=["I was charged twice"], n_results=1)
collection.update(ids=["doc-1"], documents=["Contact billing with both payment dates."])

The adapter adds the document/query prefixes, delegates to the pinned encoder, and saves its model contract as configuration. When reopening, the demo supplies the same embedding function so one lazy model instance is reused. Another Python application must import the adapter to reconstruct it from the saved configuration.

See the adapter and Chroma’s embedding-function documentation. M02’s add, query, and update calls no longer pass vectors.

Optional comparison: hybrid search

M02 also supports --method hybrid: Chroma supplies the semantic ranking, a local TF-IDF keyword search supplies another ranking, and reciprocal rank fusion (RRF) combines them. Use --method compare to inspect lexical, dense, and hybrid results together.

uv run --all-extras python -m modules.c02_vector_databases.m02_chroma_demo search --method compare --query "temporary card authorization" --top-k 3 --candidate-k 10

For each document, RRF adds 1 / (60 + rank) for every branch in which it appears. Missing branches contribute zero. The printed component ranks explain the final score; it is not a cosine similarity or a probability. Both branches use the same category filter when running the filter stage. With no keyword matches, only the dense branch contributes.

This is application-side hybrid search for local Docker Chroma. Chroma’s native hybrid Search API is currently Cloud-only. The keyword branch uses Chapter 2’s TF-IDF helper, not BM25. It reads current stored text for each query and limits this classroom approach to 1,000 eligible records. No re-embedding is needed.

Ask participants whether an exact phrase and a paraphrase produce different rankings. Inspect relevance before claiming hybrid improves quality. Keep dense search as the baseline; hybrid is optional preparation for future rag_pipelines work.

Chroma returns one inner result list per query vector. One question therefore still has a nested result shape. You can explain this as “a list of result lists—one list for each question.”

Read adding data and query versus get. The course module is m02_chroma_demo.py.

08 / Interactive illustration

Similarity ranks. Metadata restricts eligibility.

Question: “What should I do if I was billed twice?” Choose a category and a result count below. These fixed scores are invented to illustrate the behavior; this page does not run Nomic or connect to a database.

Simulator example: with k = 3, all categories return three illustrative candidates; billing returns two; an absent category returns none. A technical filter returns technical passages even though the question is about billing.

where={"category": {"$eq": "billing"}}

In the actual Chroma demo, categories are human-assigned tags derived from headings. They are not predictions made by Nomic. Filtering to the wrong category can exclude the best answer.

This describes logical eligibility, not a promise about the internal execution order of every vector database. In pgvector, filtering combined with an approximate index can reduce the result count because filtering is applied after index scanning. Chroma filters ↗ · pgvector filtering caveat ↗

Classroom exercise

Predict the results for “billing,” then “technical,” then an absent category. Discuss why requesting three results can return only two—or zero. A category filter is a retrieval rule; it is not automatically an authorization system.

09 / Keeping the store correct

Changed meaning needs a changed vector.

Before

“My router is offline and none of my devices can connect to the internet.”

Category: technical
Revision: 1

After

“My monthly invoice contains two completed charges; I need the billing team to review them.”

Category: billing
Revision: 2

The demo keeps the ID mutation-demo and supplies changed text, category, and revision. Chroma automatically recomputes the embedding through the configured function. It reads the record back and prints the size of the vector change.

If a system changes stored text without refreshing its vector, retrieval can use an outdated meaning. In this configured Chroma example, supplying changed documents without an embeddings argument triggers re-embedding automatically. A metadata-only change generally does not need a new embedding unless that metadata is also part of the encoded text.

The temporary record takes a fully populated collection from six to seven records; deletion brings it back to six. The all command performs both steps. It preserves the collection and the support passages. Update and upsert reference ↗

A practical difference between your two demos

PostgreSQL’s insert stage refreshes matching IDs. Chroma’s add stage skips matching IDs. Editing the source file and rerunning Chroma add will not update existing text. Use an explicit update/re-ingestion strategy when changing the dataset.

12 / Explain it before revealing it

Questions your students may ask.

Answer each question aloud, then expand it. These answers are also included when printing.

1. Does the vector database create the embeddings?

M01 explicitly calls the local encoder. M02 configures Nomic as a Chroma embedding function, so the Chroma Python client calls it automatically for document writes and text queries. The model still runs on your machine, not inside the Docker database server.

2. Why do both questions and documents use the same model?

They need a compatible coordinate space. The model uses different task prefixes for queries and documents, but both outputs are designed to be compared in that space.

3. Is an exact search guaranteed to answer correctly?

No. It finds the nearest vectors according to the distance metric. The nearest passage can still be irrelevant or incomplete. Answer correctness is a separate concern.

4. If top-k is three, why did the billing filter return two?

Only two records match the billing category in the current fixture. The filter restricts the eligible set; k is a maximum, not a requirement to invent or include other records.

5. Why might PostgreSQL ignore our new HNSW index?

For a tiny table, a scan and sort can be cheaper. Index existence does not guarantee index usage. Inspect the query plan instead of guessing.

6. Is HNSW the same as GraphRAG?

No. HNSW is a graph-based index over vectors used to find neighbors. GraphRAG generally retrieves using relationships among entities or other graph-structured knowledge. They solve different parts of retrieval.

7. Can I replace Nomic with another 768-dimensional model?

You can change models, but must re-embed the corpus and queries consistently. The same vector length does not establish compatibility. Use a separate store during migration and validate the new retrieval results.

8. What happens if we update the text but keep the old embedding?

If an application explicitly supplies an old vector with changed text, retrieval can be misleading. Our configured M02 instead passes changed documents without embeddings, so Chroma recomputes their vectors automatically.

9. Is Chroma better than PostgreSQL?

These small demos do not establish a winner. Compare the fit: PostgreSQL integrates vectors with SQL and relational data; Chroma exposes a collection-oriented retrieval API. Choose against your own data, operations, filtering requirements, and measured workload.

10. Are we using the Greek Magenta PDF here?

No. These two demos currently load the fictional English telecom support text. Using the Greek PDF would require document ingestion, suitable chunk metadata, and evaluation on Greek questions.

11. Does a metadata filter secure customer data?

Only if it is part of a correctly enforced access-control design. This demo’s user-selectable category is a teaching filter. Production authorization must derive permitted scope from trusted identity and enforce it consistently.

12. What persists when the Python program exits?

The database records remain in the services’ Docker volumes. Python’s loaded model and in-memory variables do not. A later search loads the encoder to embed its question and reuses the stored document vectors.
